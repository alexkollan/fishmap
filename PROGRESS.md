## Map factor layers rebuilt as a full-viewport "weather map" overlay, backend-precomputed (2026-08-22)

Requested change: the coastline should always show Overall; picking a factor (Wind, Waves, Pressure, Sea temp, Water clarity, Current, Time of day) in the Layer Drawer should instead paint a smooth full-viewport color overlay across the sea — like a real marine weather map — computed on the backend and cached, not scored live in the browser per factor.

**Backend** (new): `apps/api/src/lib/areaGrid.ts` builds a regular grid over the Greek bbox at `AREA_GRID_STEP = 0.1°` (~11km, ~7,844 cells) — finer than the existing 0.25° point/coastline grid but reusing the exact same `weather_cache` table (same `(grid_lat, grid_lon, variable_set)` key shape, no schema change). `apps/api/src/jobs/areaWeatherRefresh.ts` is a new cron (`0 */12 * * *`, plus once at startup, registered in `server.ts` next to the existing notification cron) that fetches the whole grid from Open-Meteo and lands it in that cache; `GET /api/scores/area?mode=&hourIndex=` (`apps/api/src/routes/scores.ts`) reads only from that cache (never calls upstream itself) and runs the existing `scoreHour()` per cell, returning a compact flat-array payload for just the 7 selectable factors. Individual factor scores don't depend on the weight profile (only *Overall* does), which is what makes backend-precomputing them safe without breaking the live admin weight editor — Overall stays entirely on the existing live per-segment pipeline, untouched.

**Frontend**: `useCoastlineScoring.ts`'s `paint()` now always uses Overall, full stop — the per-factor `setFeatureState` branch is gone. A new `useAreaScoreGrid.ts` hook fetches `/api/scores/area` and hands the grid to a new `areaHeatmap.worker.ts`, which paints one pixel per grid cell onto an `OffscreenCanvas` (`scoreColor.ts`, a JS port of the coastline's color ramp) and transfers back an `ImageBitmap` — no manual interpolation; MapLibre's own `raster-resampling: "linear"` does the smoothing when it stretches that coarse image across the viewport via an `image` source, inserted with `beforeId: COASTLINE_LINE_LAYER_ID` so it renders below the coastline line and below the (unchanged) overlay tile layers. `LayerDrawer.tsx` got a small color-scale legend, shown whenever a factor layer is selected.

**Found and fixed two real bugs during verification, not just wired the happy path:**
1. `apps/api/src/adapters/open-meteo.ts`'s `fetch()` calls had no timeout — a single stalled connection left the refresh cron's `await` pending forever with zero error logged, silently killing all progress. Added `AbortSignal.timeout()` (20s single-point, 45s batch).
2. Firing all ~79 batches (158 requests) back to back blew straight through Open-Meteo's per-minute rate limit — most batches came back 429/503, and `cachedBatch`'s existing stale-while-revalidate fallback silently swallowed those as "no data for this batch" (by design, for the live route) with no error surfaced anywhere. Fixed with retry-with-backoff on 429/503 in `fetchOpenMeteoBatch` (respects `Retry-After`, falls back to 65s) plus a 2s pace between batches in the job. Also hardened `GET /api/scores/area` itself: it originally 503'd unless the *exact* geographic-center grid cell had cached data yet, which is needlessly fragile against a cache that fills in incrementally — it now falls back to whichever cell has data first for the shared sun/moon reference calc, and serves whatever's cached (with nulls elsewhere) rather than all-or-nothing.

**Verified for real, not just "it builds":** `pnpm typecheck`/`pnpm test` green across the workspace; `pnpm build` confirms the new worker gets its own hashed chunk (no vendoring gotcha, unlike the MapLibre worker); ran the actual refresh cron against live Open-Meteo and confirmed sane, well-varied per-factor scores land in the cache; drove the real `/map` page with Playwright (headless Chromium, since `chromium-cli` wasn't available in this environment) — clicked every factor layer, zero console errors, legend renders — and separately mocked `/api/scores/area` with a synthetic gradient to prove the worker→canvas→MapLibre rendering chain paints a smooth full-viewport gradient (screenshot-confirmed) independent of how warm the real cache happened to be.

**Also hit, unrelated to the feature itself but worth remembering:** the long-running `pnpm dev:web` process (up since early this morning) never picked up *any* of this session's edits — confirmed by diffing what Vite's dev server actually served against what was on disk. ## Service worker never activated new deploys — "layers don't work" was stale JS, not a bug (2026-08-22)

Reported as "score layers do nothing, bathymetry shows nothing." Directly verified both features first, before assuming the report was wrong: hooked into the live MapLibre instance (`map.getFeatureState`) and confirmed score layers genuinely carry different per-factor values (Overall 50, Wind 55, Current 73 — not a coincidence), and confirmed all 12 bathymetry tile requests return 200 with the overlay rendering — both in dev *and* through a real `docker compose` stack. User's follow-up ("not at all," i.e. zero change, not a subtle one) ruled out "the color difference is just subtle" as the explanation.

Real cause: `apps/web/src/sw.ts` (the custom `injectManifest` service worker added for Web Push, replacing the previous `generateSW` default — see the map/nginx entries below) never called `self.skipWaiting()` or claimed clients. `vite.config.ts` sets `registerType: "autoUpdate"`, but that pairing (immediate takeover, no "close all tabs" limbo) is something `generateSW` injects into its generated worker automatically — it is **not** automatic for a hand-written `injectManifest` source file; the developer has to add it. Without it, every new deploy's service worker installs but sits in `waiting` state indefinitely — the *previous* version keeps controlling every already-open tab, serving whatever JS bundle it precached at install time, until the user closes every tab of the site. A returning user (or a developer's own long-lived test tab) can be running a build from days/deploys ago with no indication anything is stale — which perfectly explains "I click a feature that works in a fresh build and nothing happens."

Fix: `sw.ts` now calls `self.skipWaiting()` on `install` and `self.clients.claim()` on `activate`. Paired with a `controllerchange` listener in `main.tsx` that reloads the page exactly once — skipWaiting/clientsClaim alone would make a new worker take over control, but an already-loaded tab's already-executing JS doesn't retroactively update itself; the one-time reload is what actually completes the update for a tab left open across a deploy.

**Verified with an actual two-deploy lifecycle test, not just code inspection** (this exact bug class — "looks fixed but isn't" — has bitten this session's map work twice already, so a real repro was worth the time): opened a persistent browser tab against `docker compose`-served "version A," attached `updatefound`/`controllerchange` listeners, then rebuilt and redeployed the *same* container as "version B" (a trivial marker change to `index.html`'s `<title>`) while the tab stayed open and kept calling `registration.update()` — matching what a real browser does on navigation. The tab reloaded itself with no `page.reload()`/`page.goto()` call from the test, and picked up the new title. That confirms the whole chain — browser detects new `sw.js` bytes → installs → `skipWaiting` → `activate` → `clients.claim()` claims the open tab → `controllerchange` fires → one reload → fresh bundle — actually works end to end, not just in theory.

**Open item, same as the map/nginx fixes above:** this needs an actual redeploy to reach `fishmap.alexcoll.in`. It also means anyone who has the site open in a tab *right now*, from before this fix ships, will need one manual hard-refresh to get unstuck — after that, this class of problem shouldn't recur, since every deploy going forward self-activates.

## Production map bugfix: black map, no console errors (2026-08-22)

Reported directly against the deployed `fishmap.alexcoll.in`: the map worked fine in dev but rendered as a plain black rectangle in production — clicks/coordinate selection still worked, layers didn't show, and there were zero console errors of any kind. That last detail (no errors at all) was the key clue and took real digging to run down, since the obvious suspects (network failures, CORS, CSP) would normally show *something* in the console.

Root cause: `apps/web/src/map/MapCanvas.tsx` was pointing MapLibre at its worker via a Vite `?url` import of `maplibre-gl/dist/maplibre-gl-worker.mjs`. That worker file itself imports a sibling chunk, `./maplibre-gl-shared.mjs`, via a plain relative path — and Vite's `?url` mechanism treats the file you reference as an opaque asset; it has no way to know it also needs to emit that sibling. In dev this was invisible because `vite.config.ts` already excludes `maplibre-gl` from dependency pre-bundling (a fix from earlier this session), which serves the whole package straight from `node_modules` — every sibling file present, real relative paths. In the actual production build, only the one explicitly-referenced worker file got copied into `dist/assets/`; its `maplibre-gl-shared.mjs` dependency 404'd. And because this is an SPA with nginx's `try_files $uri $uri/ /index.html` catching unmatched routes, that 404 came back disguised as a *200 response containing `index.html`* instead of an actual error — which is exactly why nothing showed up in any console-error or failed-request check. MapLibre's `Map` object still constructed fine and click handlers still fired (both are main-thread only), but the worker — which is what actually processes and renders vector tiles — threw during module evaluation and died silently.

Confirmed by building the actual production bundle locally (`pnpm build` + `vite preview`, the same static output nginx serves) and reproducing the exact symptom before touching anything: canvas present, WebGL available, `tiles.json`/style/sprite all fetched fine, but zero actual `.mvt` tile requests ever fired. A wrapper diagnostic worker (importing the real worker module from inside another worker, to bypass the browser's error-sanitization on cross-worker `onerror`) surfaced the real underlying `TypeError: Failed to fetch dynamically imported module`.

Fix: vendored both `maplibre-gl-worker.mjs` and `maplibre-gl-shared.mjs` verbatim (unhashed) into `apps/web/public/vendor/`, so Vite copies them through untouched and their relative import to each other stays intact — see `apps/web/public/vendor/README.md` and the corresponding CLAUDE.md section for the full explanation and the "don't revert this" warning for future sessions. Re-verified against a real production build: real `.mvt` tile requests now fire, full CARTO Dark Matter basemap and coastline render correctly, screenshot-confirmed.

While investigating, also checked whether `tools/coastline-pipeline` becoming a real workspace member (earlier this session) could break `docker compose build`, since `apps/web/Dockerfile`'s `pnpm install --frozen-lockfile` step doesn't `COPY` that package's `package.json`. Tested directly by simulating the exact Dockerfile COPY sequence in an isolated directory — `pnpm install --frozen-lockfile` handles a missing/uncopied workspace member gracefully (it just doesn't try to resolve deps for a package that isn't physically present), so this turned out not to be a real problem. No Dockerfile change needed.

**Open item:** this was fixed and verified against a local production-equivalent build, but not yet re-deployed to `fishmap.alexcoll.in` itself — that's a `docker compose build && docker compose up -d` (or whatever the actual deploy step is) on the VPS, still needed from a human.

### Follow-up: the vendor fix alone wasn't enough — nginx MIME types (same day)

After deploying the vendor fix above, a second, more specific error surfaced: `Failed to load module script: The server responded with a non-JavaScript MIME type of "application/octet-stream"` for `/vendor/maplibre-gl-worker.mjs`. Progress, in a way — this is a real, visible error, unlike the silent 200-of-wrong-content failure before. Cause: `nginx:1.27-alpine`'s stock `mime.types` file has no entry for `.mjs` (it predates/never added that extension), so nginx falls back to `default_type` (`application/octet-stream`) for it — and browsers enforce strict MIME-type checking for module scripts/workers specifically (unlike classic scripts, which are more lenient), so the browser refuses to execute it outright.

**This gap existed in the previous fix because verification only went through `vite preview` (Vite's own dev-oriented static server, which has correct built-in MIME mappings) — never through the actual nginx container.** Caught and fixed properly this time by building and running the real `docker compose` stack locally (`docker compose build && docker compose up -d`, both `api` and `web` — the running `api` image was also 15 hours stale from before this session and had none of this session's routes, a second latent gap this surfaced) and hitting it directly. `curl -I` against the real container confirmed `Content-Type: application/octet-stream` before the fix and `application/javascript` after.

Fix: added a `location ~* \.mjs$ { default_type application/javascript; }` block to `apps/web/nginx.conf` — `default_type` only applies when nginx can't otherwise resolve a MIME type, so this doesn't touch any existing `.js`/`.css`/etc mappings. Re-verified end to end against the real Docker stack: `curl -I` shows the correct header, and a full Playwright pass against `http://localhost:48181/map` (the actual compose-exposed port) shows zero console errors, real `.mvt` tile requests firing, and the coastline correctly colored by live score in the screenshot.

**Lesson for future verification of anything nginx/deploy-related in this repo: `vite preview` is not a sufficient stand-in for the real container.** It shares the build output but not the serving layer, and the serving layer is exactly where this class of bug lives. Use `docker compose build && docker compose up -d` and hit the real compose-exposed port when the question is "does this actually work in production," not just `vite preview`.

## Scoring recalibration (2026-08-22)

Live feedback after Phases 1–8: the score almost never left the 55-80 range regardless of how the day actually looked — a genuinely unremarkable, nothing-going-for-it day (dead calm, bluebird midday, stable high pressure) still scored 64 ("Good"). Measured with a probe script before touching anything: the root cause was that most individual factor curves had "neutral/no-signal" baselines set too high (waves defaulted to 90-100 across the entire 0.2-0.7m band, which is the Aegean's ordinary summer state, not a special occasion; solunar bumped to 75-90 for merely being inside one of the several ~2h windows every day covers; pressure's "stable" case scored 68; precipitation's "no rain" baseline was 65 — already inside the "Good" band on its own). Averaged across 10 factors, these generous floors meant a day rarely read as anything but "Good."

Recalibrated in `packages/scoring/src/factors.ts` (see the `Recalibrated 2026-08-22` comments at each site): lowered neutral/no-data baselines across pressure, waves, turbidity, seaTemp, precipitation, solunar, current, seasonality, and calm-wind (shore + boat), and narrowed the wave "sweet spot" so ordinary chop no longer auto-maxes. The twilight-aligned solunar case and genuine falling-pressure/onshore-breeze cases still score high — what changed is that *merely adequate* conditions across the board no longer average up to "Good" by default.

Before/after on a probe script (not committed — ad hoc, reproducible from the scenarios described here) scoring realistic hand-built weather series in shore mode:

| Scenario | Before | After |
|---|---|---|
| Dead calm, bluebird midday, stable high pressure (genuinely bad) | 64 (Good) | 40 (Fair) |
| Totally unremarkable, nothing wrong or special | 64 (Good) | 58 (Good) |
| Real falling pressure, onshore breeze, dusk, overcast (genuinely great) | 78 (Very good) | 79 (Very good) |
| Every factor stacked favorably at once | — | 83 (Very good) |
| Sharp post-frontal rise, dead calm, bluebird, winter (no veto) | — | 39 (Fair) |

Boat mode's calm-wind floor (85, nearly excellent for zero wind) got the same treatment (→55). Spearfishing wasn't touched — its turbidity-dominated scoring already discriminated well (20 vs 74 on bad/great probes) without changes. Vetoes and the 0-100 band cutoffs (`apps/web/src/lib/score.ts`) are unchanged; this was a curve-shape fix, not a threshold fix.

Existing scoring tests (`packages/scoring/src/score.test.ts`) don't assert specific score values (only 0-100 bounds and veto presence), so they needed no changes and still pass. This is exactly the kind of tuning `DEV_PLAN.md` §12 anticipated ("assume v1 weights are a hypothesis, not truth") — the admin live weight editor (Phase 7) still lets Alex retune weights per-mode on top of this without touching code, but the underlying curve shapes needed a code change since the old floors were structural, not a weighting problem.

### Follow-up: weight rebalancing (same day)

Curve recalibration alone wasn't quite enough — checking real live conditions (`GET /api/weather`, scored through `scoreHour` directly) turned up a concrete case: a midnight spearfishing check scored 69 ("Good") because `turbidity`/`waves`/`wind` all happened to read excellent (calm, clear water) and `light` — correctly reading 15 for pitch dark — was only ~11% of spearfishing's total weight, too little to overrule the other three. Same root issue as the curve problem, different mechanism: the two most evidence-backed factors (`pressure`, and `light`/time-of-day — DEV_PLAN.md §4.6 calls light "the strongest single predictor") weren't weighted like it, while `solunar` (explicitly flagged in `factors.ts` as contested science) and `current` carried more influence than their evidence quality justifies.

Rebalanced `DEFAULT_WEIGHT_PROFILES` in `packages/scoring/src/weights.ts` (all three modes): pressure and light both moved up meaningfully, seasonality moved up (it was underweighted relative to how well it now discriminates post-recalibration), solunar and current moved down. Spearfishing's `light` weight roughly doubled (10→20, now tied for spearfishing's single highest weight alongside turbidity) specifically because of the midnight case above.

Effect, live Athens conditions at the time of the change (stable pressure, clear calm night, 27°C SST, August):

| Mode | Before rebalance | After |
|---|---|---|
| Shore | 50 | 51 (flat — wasn't the problem case here) |
| Boat | 58 | 58 (flat) |
| Spearfishing (the midnight case) | 69 (Good) | 60 (Good, but meaningfully closer to Fair) |

And on the synthetic scenarios from the curve-recalibration table above: the genuinely great shore day actually moved *up* (79→81, since pressure/light being weighted higher rewards real alignment on those too, not just punishes their absence), the bad/mediocre shore days stayed roughly flat (38, 57) — confirming the rebalance sharpens discrimination rather than just dragging everything down uniformly.

Spearfishing's midnight case (60) is better but still landed in "Good," not "Fair" as of the previous fix — `turbidity`+`waves`+`wind` together are still ~49% of spearfishing's weight even after trimming, partly by design (DEV_PLAN.md explicitly calls turbidity spearfishing's single highest-priority factor, citing diver forums ranking visibility above even wave height/safety — this rebalance trimmed that citation-backed weighting rather than discarding it). See the band-relabelling entry directly below — it resolves this specific case too, without further weight surgery.

### Follow-up: score-band thresholds and wording (same day)

Even after the weight rebalance above, live-checking current conditions still showed the same shape of problem one layer up: a thoroughly unremarkable shore day (score 50-51) was labelled "Good," and the resolved spearfishing midnight case (60) was *also* still "Good." The scoring itself had gotten meaningfully more honest — the presentation layer (`apps/web/src/lib/score.ts`'s `scoreBandKey` cutoffs, `<=69` for "good") hadn't caught up, so a score in the newly-legitimate "unremarkable" 45-62 range was still reading as a positive verdict.

Widened the bands so "good" requires clearing a real bar, and relabelled the band below it from the softer "Fair" to the blunter "Meh" (English only — the Greek "Μέτρια" already reads as bluntly as "mediocre," it was the English wording and the threshold both that were too soft):

```
poor  (Bad):        <= 44   (was <= 29)
fair  (Meh):         <= 62   (was <= 49, label was "Fair")
good  (Good):        <= 76   (was <= 69)
veryGood (Very good): <= 88  (was <= 84)
excellent:           > 88    (was > 84)
```

Live-checked against real Athens conditions at the time: shore 51, boat 58, and the spearfishing midnight case (60) all now read "Meh" instead of "Good" — the exact case the weight rebalance above couldn't fully resolve on its own, resolved instead by being honest about where the boundary sits. A genuinely great shore day (81, real falling pressure + onshore breeze + dusk) reads "Very good"; a genuinely bad one (38, post-frontal rise + dead calm + winter) reads "Bad." Verified live in the browser in both languages (screenshot-checked, not just typechecked).

`scoreColor()` (the green→amber→red gradient) is unchanged — only the discrete band labels and their thresholds moved. This is presentation-layer only; `packages/scoring` and its weights/curves are untouched by this specific follow-up.

### Phase 3+5 — Map foundation and coastline scoring

- **MapLibre + CARTO Dark Matter**, lazy-loaded on `/map` only (`React.lazy` in `App.tsx` — it was a synchronous import before this session, now fixed to match §5.6).
- **Coastline rendering is plain GeoJSON + `setFeatureState`, not MVT vector tiles.** `tippecanoe` is unavailable in this environment (not installable without sudo) and there's no `gdal`/`ogr2ogr` either. Real MVT tiling per §5.1 is not done. Instead: `tools/coastline-pipeline/build.mjs` clips a Natural Earth 10m coastline (fetched from a GitHub mirror of `ne_10m_coastline`/`ne_10m_land`) to the Greek bbox, chunks it into ~1.5 km segments (`turf.lineChunk`), and computes each segment's seaward-facing `aspectDeg` via point-in-polygon land tests offset from the segment normal. Output: `apps/web/public/data/coastline.geojson`, 8,965 segments, ~430 KB gzipped, served as a static file. MapLibre renders it as one GeoJSON source with a `line-color` data-driven expression reading `setFeatureState`. This works and performs well at the scale tested (whole-Greece pan/zoom, live in a real browser) but is lower-fidelity than a real OSM+tippecanoe pipeline — fewer, smoother segments, no 250 m near-harbor detail per §11.1. Re-running the pipeline needs the raw Natural Earth GeoJSON files (URLs in `tools/coastline-pipeline/build.mjs` comments); it doesn't re-download them itself.
- **Weather grid fetch** (`GET /api/weather/grid?points=lat,lon;...`): batches up to 120 points per request (Open-Meteo accepts comma-joined coords and returns an array), cache-aside via a new `cachedBatch()` in `db/cache.ts` alongside the existing single-point `cached()`. The map fetches only grid cells intersecting the current viewport (padded), chunked client-side at 100 points/request, tracked so a pan never re-fetches an already-seen cell.
- **Scoring uses nearest-grid-cell, not true bilinear interpolation.** §5.2 calls for bilinear; each coastline segment has a pre-baked `gridLat`/`gridLon` (nearest 0.25° cell, computed once in the pipeline) and the client-side worker just looks up that cell's series directly. Simpler, and still spatially smooth at 25 km grid spacing, but a deviation from the spec worth revisiting if scores ever look too "blocky" near grid boundaries.
- **Web Worker** (`apps/web/src/map/scoring.worker.ts`) scores every fetched segment × hour via the same `@fishmap/scoring` functions everything else uses — no second scoring implementation. Also computes a sampled (≤150 segments) whole-week sparkline for the time scrubber in one pass, and returns **every factor's score per segment**, not just the overall, so the layer drawer's per-parameter view (§6.4) never needs a second worker round-trip.
- **Wind is now genuinely direction-relative-to-shore on the map** (`windRelative()` in `packages/scoring/src/factors.ts` takes `aspectDeg`), computing onshore/offshore/cross-shore from the segment's aspect vs. `windDirection10m`. This was the biggest flagged gap from Phase 2 (PROGRESS.md previously said "scores speed alone") and is now real — but **only on the map**. Single-point pages (`/`, `/conditions/wind`, etc.) still score wind by speed alone, since a searched location has no coastline segment to source an aspect from; this matches the plan's architecture (aspect is segment-level data) and is called out in the wind page's copy.
- **Time scrubber** (`apps/web/src/map/TimeScrubber.tsx`): full fetched range (past_days=2 + forecast_days=7), inline SVG sparkline, "Now" reset button. Scrubbing does zero network requests (§5.2's whole point) — confirmed live.
- **Spot detail sheet** (`SpotSheet.tsx`): tap a coastline segment or open water → bottom sheet with score, vetoes, factor breakdown, sun/moon strip, links to every `/conditions/*` page for that exact point. Reuses `useConditions` (the single-point path) rather than the map's own worker/grid data, so it's consistent with how every other page scores — the aspect-relative wind bonus above therefore doesn't apply inside the sheet, only to the coastline's own color.
- **Mode switch** on the map reads/writes the same `useModeStore` as the rest of the app.

### Phase 8 — Notifications and polish

- **Web Push, VAPID, full subscribe/unsubscribe flow.** `push_subscriptions` table matches §7.4's preference set (locations max 5, threshold, mode, lookahead, quiet hours, max frequency, alert types). `apps/web/src/lib/push/subscribe.ts` handles the `Notification.requestPermission()` → `pushManager.subscribe()` → `POST /api/push/subscribe` chain, gated on a user gesture (the Settings save button) per §7.3's rule applied to push too. iOS standalone-mode detection gates the whole feature on that platform per §7.2.
- **The service worker strategy changed from `generateSW` to `injectManifest`** (`vite.config.ts`, new `apps/web/src/sw.ts`) — this was necessary, not optional: `generateSW`'s stock service worker has no `push` event listener, and a push payload the SW doesn't call `showNotification()` for is silently dropped by the browser. `sw.ts` adds `push` (shows the notification) and `notificationclick` (focuses/opens the deep-linked URL, never `/map` per §5.6) handlers, plus the standard `precacheAndRoute`. `sw.ts` is excluded from the main `tsconfig.json`'s type-checking scope (`ServiceWorkerGlobalScope`/`PushEvent`/etc. aren't in the DOM lib the rest of the app compiles against, and mixing WebWorker+DOM libs in one tsconfig causes global conflicts) — vite-plugin-pwa bundles it independently via esbuild regardless, so this doesn't affect the actual build. Verified: `pnpm build` produces `dist/sw.js` (injectManifest mode, 27 precache entries) with no errors.
- **Hourly cron** (`node-cron`, in `apps/api/src/server.ts` → `apps/api/src/jobs/notifications.ts`): batches subscribers by grid cell, evaluates each against their own threshold/quiet-hours/frequency cap, **safety alerts bypass both** per spec, prunes subscriptions on a 404/410 from the push service. **Not verified end-to-end with a real push service** — that needs a real device/browser subscribed to a real push endpoint (FCM/APNS), which isn't reachable from this environment. The code path is exercised by construction (same scoring functions, same DB, real VAPID keys generated this session) but no actual notification has been confirmed to arrive on a device.
- **Notification body text is English-only.** Unlike the UI (see below), the cron composes push notification titles/bodies as plain English strings (`jobs/notifications.ts`) rather than through the `noteKey`/`renderFactorNote` system, since that system lives in the web app's i18n layer and the API has no equivalent. A Greek user who enables push will get English notification text. Flagged, not silently shipped — would need a small duplicate translation table in the API (or a shared package) to fix.
- **Best windows** (`/windows`): scans every fetched hour across the active location + all saved user spots, ranks by score, de-duplicates near-adjacent hours per location (3h minimum gap) so the list isn't 6 consecutive hours at the same spot. Verified live with real ranked results.
- **User spots**: IndexedDB via `idb-keyval` + Zustand persist (`apps/web/src/spots/userSpotsStore.ts`), export-to-JSON and import-and-merge both work, verified live (`/spots` page, both the user list and the public list from `GET /api/spots`).
- **Deep links avoid `/map`**: notification `url`s point at `/` or `/forecast`, matching §5.6.
