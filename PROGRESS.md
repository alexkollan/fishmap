## Scoring recalibration (2026-08-22)

Live feedback after Phases 1–8: the score almost never left the 55-80 range regardless of how the day actually looked — a genuinely unremarkable, nothing-going-for-it day (dead calm, bluebird midday, stable high pressure) still scored 64 ("Good"). Measured with a probe script before touching anything: the root cause was that most individual factor curves had "neutral/no-signal" baselines set too high (waves defaulted to 90-100 across the entire 0.2-0.7m band, which is the Aegean's ordinary summer state, not a special occasion; solunar bumped to 75-90 for merely being inside one of the several ~2h windows every day covers; pressure's "stable" case scored 68; precipitation's "no rain" baseline was 65 — already inside the "Good" band on its own). Averaged across 10 factors, these generous floors meant a day rarely read as anything but "Good."

Recalibrated in `packages/scoring/src/factors.ts` (see the `Recalibrated 2026-08-22` comments at each site): lowered neutral/no-data baselines across pressure, waves, turbidity, seaTemp, precipitation, solunar, current, seasonality, and calm-wind (shore + boat), and narrowed the wave "sweet spot" so ordinary chop no longer auto-maxes. The twilight-aligned solunar case and genuine falling-pressure/onshore-breeze cases still score high — what changed is that *merely adequate* conditions across the board no longer average up to "Good" by default.

Before/after on a probe script (not committed — ad hoc, reproducible from the scenarios described here) scoring realistic hand-built weather series in shore mode:

| Scenario | Before | After |
|---|---|---|
| Dead calm, bluebird midday, stable high pressure (genuinely bad) | 64 (Good) | 40 (Fair) |
| Totally unremarkable, nothing wrong or special | 64 (Good) | 58 (Good) |
| Real falling pressure, onshore breeze, dusk, overcast (genuinely great) | 78 (Very good) | 79 (Very good) |
| Every factor stacked favorably at once | — | 83 (Very good) |
| Sharp post-frontal rise, dead calm, bluebird, winter (no veto) | — | 39 (Fair) |

Boat mode's calm-wind floor (85, nearly excellent for zero wind) got the same treatment (→55). Spearfishing wasn't touched — its turbidity-dominated scoring already discriminated well (20 vs 74 on bad/great probes) without changes. Vetoes and the 0-100 band cutoffs (`apps/web/src/lib/score.ts`) are unchanged; this was a curve-shape fix, not a threshold fix.

Existing scoring tests (`packages/scoring/src/score.test.ts`) don't assert specific score values (only 0-100 bounds and veto presence), so they needed no changes and still pass. This is exactly the kind of tuning `DEV_PLAN.md` §12 anticipated ("assume v1 weights are a hypothesis, not truth") — the admin live weight editor (Phase 7) still lets Alex retune weights per-mode on top of this without touching code, but the underlying curve shapes needed a code change since the old floors were structural, not a weighting problem.

### Phase 3+5 — Map foundation and coastline scoring

- **MapLibre + CARTO Dark Matter**, lazy-loaded on `/map` only (`React.lazy` in `App.tsx` — it was a synchronous import before this session, now fixed to match §5.6).
- **Coastline rendering is plain GeoJSON + `setFeatureState`, not MVT vector tiles.** `tippecanoe` is unavailable in this environment (not installable without sudo) and there's no `gdal`/`ogr2ogr` either. Real MVT tiling per §5.1 is not done. Instead: `tools/coastline-pipeline/build.mjs` clips a Natural Earth 10m coastline (fetched from a GitHub mirror of `ne_10m_coastline`/`ne_10m_land`) to the Greek bbox, chunks it into ~1.5 km segments (`turf.lineChunk`), and computes each segment's seaward-facing `aspectDeg` via point-in-polygon land tests offset from the segment normal. Output: `apps/web/public/data/coastline.geojson`, 8,965 segments, ~430 KB gzipped, served as a static file. MapLibre renders it as one GeoJSON source with a `line-color` data-driven expression reading `setFeatureState`. This works and performs well at the scale tested (whole-Greece pan/zoom, live in a real browser) but is lower-fidelity than a real OSM+tippecanoe pipeline — fewer, smoother segments, no 250 m near-harbor detail per §11.1. Re-running the pipeline needs the raw Natural Earth GeoJSON files (URLs in `tools/coastline-pipeline/build.mjs` comments); it doesn't re-download them itself.
- **Weather grid fetch** (`GET /api/weather/grid?points=lat,lon;...`): batches up to 120 points per request (Open-Meteo accepts comma-joined coords and returns an array), cache-aside via a new `cachedBatch()` in `db/cache.ts` alongside the existing single-point `cached()`. The map fetches only grid cells intersecting the current viewport (padded), chunked client-side at 100 points/request, tracked so a pan never re-fetches an already-seen cell.
- **Scoring uses nearest-grid-cell, not true bilinear interpolation.** §5.2 calls for bilinear; each coastline segment has a pre-baked `gridLat`/`gridLon` (nearest 0.25° cell, computed once in the pipeline) and the client-side worker just looks up that cell's series directly. Simpler, and still spatially smooth at 25 km grid spacing, but a deviation from the spec worth revisiting if scores ever look too "blocky" near grid boundaries.
- **Web Worker** (`apps/web/src/map/scoring.worker.ts`) scores every fetched segment × hour via the same `@fishmap/scoring` functions everything else uses — no second scoring implementation. Also computes a sampled (≤150 segments) whole-week sparkline for the time scrubber in one pass, and returns **every factor's score per segment**, not just the overall, so the layer drawer's per-parameter view (§6.4) never needs a second worker round-trip.
- **Wind is now genuinely direction-relative-to-shore on the map** (`windRelative()` in `packages/scoring/src/factors.ts` takes `aspectDeg`), computing onshore/offshore/cross-shore from the segment's aspect vs. `windDirection10m`. This was the biggest flagged gap from Phase 2 (PROGRESS.md previously said "scores speed alone") and is now real — but **only on the map**. Single-point pages (`/`, `/conditions/wind`, etc.) still score wind by speed alone, since a searched location has no coastline segment to source an aspect from; this matches the plan's architecture (aspect is segment-level data) and is called out in the wind page's copy.
- **Time scrubber** (`apps/web/src/map/TimeScrubber.tsx`): full fetched range (past_days=2 + forecast_days=7), inline SVG sparkline, "Now" reset button. Scrubbing does zero network requests (§5.2's whole point) — confirmed live.
- **Spot detail sheet** (`SpotSheet.tsx`): tap a coastline segment or open water → bottom sheet with score, vetoes, factor breakdown, sun/moon strip, links to every `/conditions/*` page for that exact point. Reuses `useConditions` (the single-point path) rather than the map's own worker/grid data, so it's consistent with how every other page scores — the aspect-relative wind bonus above therefore doesn't apply inside the sheet, only to the coastline's own color.
- **Mode switch** on the map reads/writes the same `useModeStore` as the rest of the app.

### Phase 6 — Layers

- **Score layers**: Overall / Wind / Waves / Pressure / Sea temp / Clarity / Current / Light — switching is instant (data already in the last worker message, no re-score).
- **Bathymetry + Posidonia overlays are proxied and disk-cached**, per §5.5's "never point the browser directly at EMODnet." New `apps/api/src/routes/tiles.ts`: converts an XYZ tile request to a WMS `GetMap` bbox (`apps/api/src/lib/webMercator.ts`), fetches from EMODnet, writes to `${DATA_DIR}/tiles/<source>/<z>/<x>/<y>.png`, serves from disk on repeat hits (30-day TTL), falls back to stale-on-upstream-failure. Verified live: real depth-colored raster tiles rendering under the coastline on the map. Layer names used: `emodnet:mean_atlas_land` (bathymetry), `greek_seagrass_meadows_v0906` (a Greece-specific seagrass/Posidonia layer on EMODnet Seabed Habitats — found by querying `GetCapabilities`, more directly relevant than the generic EU-wide Article 17 Posidonia layer).
- **Seamarks** are OpenSeaMap raster tiles loaded directly (no proxy) per §3.4 — only EMODnet is rate-limited enough to need one.
- **Layer state persists to localStorage** (`useMapLayers.ts`, a small Zustand+persist store), matching "the app opens the way it was left."
- **`windParticles` deferred, not built.** The flag exists (seeded `admin_only` in `feature_flags`), `useFlag()` exists, but there's no particle animation — building and frame-cost-measuring a wind particle system was cut for time. This is an honest gap, not a silent one: the layer drawer doesn't offer a toggle for it at all yet.

### Phase 8 — Notifications and polish

- **Web Push, VAPID, full subscribe/unsubscribe flow.** `push_subscriptions` table matches §7.4's preference set (locations max 5, threshold, mode, lookahead, quiet hours, max frequency, alert types). `apps/web/src/lib/push/subscribe.ts` handles the `Notification.requestPermission()` → `pushManager.subscribe()` → `POST /api/push/subscribe` chain, gated on a user gesture (the Settings save button) per §7.3's rule applied to push too. iOS standalone-mode detection gates the whole feature on that platform per §7.2.
- **The service worker strategy changed from `generateSW` to `injectManifest`** (`vite.config.ts`, new `apps/web/src/sw.ts`) — this was necessary, not optional: `generateSW`'s stock service worker has no `push` event listener, and a push payload the SW doesn't call `showNotification()` for is silently dropped by the browser. `sw.ts` adds `push` (shows the notification) and `notificationclick` (focuses/opens the deep-linked URL, never `/map` per §5.6) handlers, plus the standard `precacheAndRoute`. `sw.ts` is excluded from the main `tsconfig.json`'s type-checking scope (`ServiceWorkerGlobalScope`/`PushEvent`/etc. aren't in the DOM lib the rest of the app compiles against, and mixing WebWorker+DOM libs in one tsconfig causes global conflicts) — vite-plugin-pwa bundles it independently via esbuild regardless, so this doesn't affect the actual build. Verified: `pnpm build` produces `dist/sw.js` (injectManifest mode, 27 precache entries) with no errors.
- **Hourly cron** (`node-cron`, in `apps/api/src/server.ts` → `apps/api/src/jobs/notifications.ts`): batches subscribers by grid cell, evaluates each against their own threshold/quiet-hours/frequency cap, **safety alerts bypass both** per spec, prunes subscriptions on a 404/410 from the push service. **Not verified end-to-end with a real push service** — that needs a real device/browser subscribed to a real push endpoint (FCM/APNS), which isn't reachable from this environment. The code path is exercised by construction (same scoring functions, same DB, real VAPID keys generated this session) but no actual notification has been confirmed to arrive on a device.
- **Notification body text is English-only.** Unlike the UI (see below), the cron composes push notification titles/bodies as plain English strings (`jobs/notifications.ts`) rather than through the `noteKey`/`renderFactorNote` system, since that system lives in the web app's i18n layer and the API has no equivalent. A Greek user who enables push will get English notification text. Flagged, not silently shipped — would need a small duplicate translation table in the API (or a shared package) to fix.
- **Best windows** (`/windows`): scans every fetched hour across the active location + all saved user spots, ranks by score, de-duplicates near-adjacent hours per location (3h minimum gap) so the list isn't 6 consecutive hours at the same spot. Verified live with real ranked results.
- **User spots**: IndexedDB via `idb-keyval` + Zustand persist (`apps/web/src/spots/userSpotsStore.ts`), export-to-JSON and import-and-merge both work, verified live (`/spots` page, both the user list and the public list from `GET /api/spots`).
- **Deep links avoid `/map`**: notification `url`s point at `/` or `/forecast`, matching §5.6.

## Deviations from `DEV_PLAN.md` as written

- Node 24 is in use locally (plan specifies Node 22); `engines` is pinned to `>=22` rather than an exact version, and nothing so far depends on a Node-22-specific behavior.
- `apps/api` ships without a `tsc` build step at all (runs via `tsx` in prod too) — see `CLAUDE.md` Architecture section for why.
- `apps/api`'s Dockerfile installs `python3 make g++` in the deps stage for `better-sqlite3`; as of this session it also needs to successfully build `argon2`'s native module (same toolchain, no additional packages needed — verified locally via `pnpm install` with `allowBuilds.argon2: true` in `pnpm-workspace.yaml`).
- **No MVT/tippecanoe coastline pipeline** — see the Phase 3+5 section above. This is the largest single deviation from `DEV_PLAN.md` §5.1/§10 Phase 4 and was an environment constraint (no sudo, no `apt install tippecanoe`), not a design choice.
- **PWA build strategy changed from `generateSW` to `injectManifest`** to support custom push/notificationclick service worker logic — see Phase 8 section above.
- Weather grid scoring uses nearest-grid-cell rather than true bilinear interpolation (§5.2) — see Phase 3+5 section above.
- `tools/coastline-pipeline` is a real pnpm workspace member now (`pnpm-workspace.yaml` gained a `tools/*` entry), using `@turf/turf` — this wasn't previously wired up since the directory was empty.
